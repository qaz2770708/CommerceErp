# 账号、权限与操作审计（6.3 更新）

## 当前范围

正式工作区使用独立企业和仓库标识，店铺由管理员维护；演示工作区保留原模拟资料。客服、仓储、财务、观察员均可选择一个或多个店铺；管理员必须全选。所有账号仍须授权现有仓库，多企业和多仓不在本版范围内。

角色是固定模板。所有角色可查看授权范围内的订单与售后业务详情。

| 角色 | 可写入业务 | 额外读取模块 |
| --- | --- | --- |
| 管理员 | 全部现有功能、账号、接入准备和 SKU 映射 | 全部 |
| 客服 | 接单、审单、更正、取消；售后申请、批准、拒绝、撤回、结案 | 授权店铺订单和售后 |
| 仓储 | 补货、库存策略、仓储作业、售后质检 | 库存、仓储 |
| 财务 | 账单、成本、费用、匹配、财务导出；退款凭证 | 财务 |
| 观察员 | 无业务写入 | 库存、仓储、财务 |

售后协作流程为客服创建/审批、仓储质检、财务登记退款凭证、客服结案，相关订单必须在各账号授权范围内。真实平台退款不在本次范围内。

共享仓的补货、冻结/安全库存策略及余额按仓库管理，会影响所有店铺。普通库存流水同时检查订单和出库单（含多订单合单），隔离库存流水检查售后单所属店铺；无订单的期初/补货等仓级流水仍可见。筛选后的流水不是完整仓库对账结果。

公共 SKU 条码和未来出库单位成本影响全部店铺，修改仍要求相应角色且授权全部四家店铺；部分授权可读取公共配置。全库业务一致性审计也要求全店授权。桌面相应按钮禁用，直接 HTTP 调用仍会拒绝。

财务导出包按其中全部订单检查授权；混合店铺包不会被截断成部分内容，任一订单未授权则整包不可见、不可下载，也不能标记已保存。改权立即撤销旧会话，新会话重新检查授权。

## 首次管理员

本地首次启动显示初始化窗口，无默认生产密码。账号名 3–32 位英文字母、数字、点、下划线或横线，按小写存储；显示名最多 50 字；密码 12–128 个非控制字符。

共享服务的 HTTP 初始化要求连接令牌、回环来源和库内无账号。已有账号后入口关闭。也可以在服务机器的交互式终端运行：

```powershell
# SQLite：填服务器实际使用的数据目录
./app/tools/CommerceErp.DatabaseTool.exe create-admin --data 'D:/ERP/server-data'
# SQL Server：先在本机配置 ERP_SQL_CONNECTION
./app/tools/CommerceErp.DatabaseTool.exe create-admin
```

工具输入密码时不回显，不接受重定向输入，也不会重置已有管理员。初始化时不要把回环管理端口置于对外反向代理之后；由部署管理员保护服务机、数据目录和连接令牌。

账号管理必须填写原因。不能停用或降级最后一个有效管理员；新账号和重置密码后首次登录必须改密。角色、范围、启停和密码变更会递增账号版本并撤销旧会话。本人改密后退出工作区，再启动登录。管理员修改自身账号后同样需要重新登录。

## 身份和会话

- 密码使用 ASP.NET Core `PasswordHasher` Identity V3，显式配置 210,000 次迭代，由框架生成随机盐及哈希格式。
- 256 位随机会话令牌仅保存在客户端内存，数据库保存 SHA-256 摘要；绝对有效期 8 小时，无自动刷新或“记住账号密码”。
- 连续 5 次错误密码锁定 15 分钟，管理员重置密码可清除锁定。不存在、停用、锁定及密码错误返回统一认证失败消息。
- 登录、初始化和本人改密共享每来源 IP 每分钟 60 次固定窗口限额，不排队。限流按服务进程生效，尚非集群全局限流；共用出口的用户共用额度。
- 业务请求需要 `X-Erp-Session` 连接令牌和 `Authorization: Bearer <账号会话>`；连接令牌不能代替人员身份。桌面同时发送 `X-Erp-Database`。
- 远端要求 HTTPS。账号密码和会话令牌不写入配置或重试日志。原有连接令牌可选 Windows 用户加密保存，失败时保持单次输入。

## 授权、重试和审计

每个业务路由在 `EndpointPermissions` 声明策略，新接口未声明则拒绝。事务入口 `SecurityContext.Run` 再次从数据库检查账号版本、会话、角色和范围。HTTP 资源检查阻止越权详情和修改，列表店铺过滤先于分页及总数计算。可信本机工具和后台工作不使用 HTTP 人员会话，须依靠数据库权限与文件 ACL 管理。

字段名按 JSON 契约兼容大小写，重复字段拒绝；改变 OperationId 大小写不能绕过归属。客户端提供的 actor 由服务端替换为“账号名 (账号ID)”。旧业务人工标签不被追改；6.2 起访问审计明确记录登录身份。

新操作号在 `SecurityOperationOwners` 绑定账号；同账号可按原请求幂等重放，其他账号（包括管理员）不能接管。历史未绑定操作仅管理员可核实接管。桌面 `pending-account.txt` 与日志同目录，有未确认操作时必须由原账号登录。不要删除绑定文件以规避恢复检查，应先核对服务端实际结果。

停用/改权与业务写入遵守同一事务锁协议。先取得事务锁且已完成检查的业务可能先提交；权限变更提交后开始的事务会拒绝旧会话。该保证不表示撤销已提交业务。

审计记录账号 ID/名称、动作、资源、结果、操作号及 UTC 时间。账号保存和重置另记录原因，原有业务理由保留在业务历史中。业务和成功审计同事务提交；异常回滚不生成成功审计；登录失败及权限拒绝另记录。界面按每页 50 条查询，数据库保留全部。可组合筛选账号（名称包含或账号 ID 精确）、动作（精确值，如 AccessDenied、POST、SaveAccount）、结果、资源包含/操作号精确及日期。界面日期按本地时区转换为 UTC；API 时间使用带时区的 ISO 8601 O 格式。新查询固定最大审计 ID，翻页不受随后追加记录影响；刷新生成新结果。

导出使用当前已查询的筛选与快照，导出全部匹配记录而非仅当前页，上限 10,000 条；超限须缩小条件。修改筛选控件后先点查询。JSON 保留字段类型，附 SHA-256 文件用于核对传输/保存完整性，不是数字签名或防篡改存证。导出原因必填，记录数量、摘要和导出账号；导出后自身审计在下一次刷新可见。

暂未实现外部不可篡改归档以及所有读取请求的逐次审计；应用角色也不限制数据库管理员。旧 GET /api/security/audit 保留最近 200 条兼容行为；新界面使用 /api/security/audit/query 和 POST /api/security/audit/export。

## 收件信息展示

观察员获得的仓储 DTO 在服务器端隐藏收件人、电话、区县、街道、邮编；省市保留。仓储操作历史的原因与附加 JSON、平台回传错误与回执也隐藏，防止其中携带收件信息。管理员、仓储具备 personal.read；客服具备该权限，但仍不能绕过仓储模块访问权限。财务无仓储读取入口。

这是固定角色下的结构化收件字段最小展示规则，尚无逐字段自定义授权，也未实施数据库静态加密。任意自由文本备注、旧导出文件或人工粘贴到其他业务字段的个人信息不在自动识别清洗范围内。下载到本机的历史文件不会随服务器改权自动撤回。

## 管理员失联恢复

仅服务机器上的受信交互式 DatabaseTool 提供恢复，无网络恢复入口。先停止业务写入并备份库，再执行身份检查；identity 仅以只读方式查询已有库，不创建库或迁移。

```powershell
# 本地 SQLite，目录须为实际数据目录
./app/tools/CommerceErp.DatabaseTool.exe identity --data 'D:/ERP/server-data'
# 把上一步 InstanceId 填入；不是密码
./app/tools/CommerceErp.DatabaseTool.exe recover-admin --data 'D:/ERP/server-data' --instance <InstanceId>
# SQL Server：本机设置 ERP_SQL_CONNECTION 后省略 --data
./app/tools/CommerceErp.DatabaseTool.exe identity
./app/tools/CommerceErp.DatabaseTool.exe recover-admin --instance <InstanceId>
```

工具核对 schema 8 与实例身份，交互输入现有管理员账号、原因和不回显的临时密码。不能新建管理员或提升普通账号；恢复将启用管理员、清除锁定、恢复全店范围、强制下次改密并撤销数据库内全部账号会话。操作审计记录 OS 用户、账号 ID 与原因，不记录密码。数据库身份不符或目标不是管理员时事务无变更。使用者必须拥有可信本机/数据库权限；该机制不能防御已取得数据库管理权限的人。

## 升级

1. 完整备份、停止全部旧服务与客户端、核清待重试操作。旧协议 1/2/3/4 与本版协议 6 禁止混用。6.5.1 使用 schema 9。
2. SQLite 首次打开自动升级至 schema 8，保留旧业务历史；首次使用建立管理员。
3. SQL Server 先在本机设置 ERP_SQL_CONNECTION，以有 DDL 权限的升级账户执行：

```powershell
# schema 5 先执行，升级至 6；schema 6/7/8 重跑无变更。
./app/tools/CommerceErp.DatabaseTool.exe upgrade-accounts --database CommerceErp_Test
# schema 6 再执行，升级至 7；schema 7/8 重跑无变更。
./app/tools/CommerceErp.DatabaseTool.exe upgrade-tasks --database CommerceErp_Test
# schema 7 升级至 8；schema 8 重跑无变更。
./app/tools/CommerceErp.DatabaseTool.exe upgrade-master --database CommerceErp_Test
```

三个升级均在事务内使用应用锁，依次处理身份有效的 schema 5、6 和 7。保留原数据库身份；服务启动不会自动升级共享库。之后在服务机器建立管理员，再开启新版服务和客户端。

回退需要停服、恢复升级前完整备份和匹配的旧程序，不能让旧程序直接读取 schema 8。

跨库迁移仅接受空目标库，保留账号、密码哈希、授权、归属和审计，但排除 SecuritySessions，用户需重新登录；目标数据库重新生成身份，报告列出排除表。

**SQL Server 实机升级、迁移和账号联调未在本环境执行。T-SQL 解析通过不代表数据库联调通过。** 请在专用测试库验证升级、恢复、权限和完整业务流程。

## 6.3 任务权限

所有已完成改密的启用账号可打开任务页，数据按业务类型和范围过滤。订单事件按店铺范围查看；其人工重试仅管理员和有该店授权的客服可执行。共享库存事件需库存读取权限，重试需库存写入权限；仓储可处理库存事件，不能借此重试订单事件。发货任务沿用仓储权限及出库单全部来源店铺检查。财务只能查看授权店铺的订单事件，不能重试；观察员不能重试。共享库存事件按仓库授权展示，不代表某一家店铺独占库存。

详情与重试逐次在数据库事务中核对会话和范围。操作号绑定真实账号；调用方伪造 actor 无效。任务历史不提供原始载荷、原始回执或连接器异常文本，人工原因遵循既有资料可见性规则。任务不提供删除、跳过前序或强制确认按钮。角色变更后旧会话仍按原有机制撤销。

## 6.5.1 审批权限

主数据读取为 master.read，期初操作分 opening.write、opening.approve、opening.policy。对应 OpeningClerk、OpeningApprover、OpeningPolicyManager；管理员保留全部能力，但策略申请人不能自批。HTTP路由均有显式策略，写事务重新核对会话、角色、店铺、仓库和操作号归属。全部范围的三类新角色可进入资料页，其他主数据保存仍仅管理员可用。

配置独立于历史保存；缺失则阻止操作。策略申请和批准要求个人账号；已开启双审的单据保存自身要求，不因后来关闭全局策略而放宽。制单人与所有修改人按稳定账号ID核对。管理账号/角色的管理员及数据库管理员仍是信任边界，不提供防串通保证。

## 6.6 库存作业

仓储角色制单、InventoryApprover审核，管理员不能自审或审核自己修改的单据；共享仓单据要求全部店铺和仓库授权。草稿和冲销均有稳定操作号。正式HTTP快捷补货已禁止，改为有依据的单据审批。schema9执行upgrade-inventory至10；SQLite自动升级。SQL实机专项未执行，不能以解析通过替代。库存单据不包含估值和财务凭证。
